# シミュレーションでは動くのに、FPGAでは動かない

> タグ: CPU自作 / FPGA / デバッグ / タイミング / Block RAM / ロジックアナライザ

テストがすべて通った回路でも、FPGAへ書き込むと止まることがあります。森羅万象CPUでも、シミュレーション上のload/storeが成功する一方で、実機では期待どおり動かない時期がありました。

これは「シミュレーションが無意味」という話ではありません。シミュレーションの前提と、合成後の回路や外部配線の条件に差があるということです。

## 3つの段階を分ける

FPGAへ届くまでには複数の段階があります。

1. HDLをシミュレーションする
2. HDLから論理回路を合成し、配置配線する
3. FPGAへ書き込み、外部回路と一緒に動かす

シミュレーションでは理想的なクロックと信号を入力できます。実機ではクロックの制約、ピン配置、I/O電圧、外部信号との同期、配線が加わります。

## 最小構成へ戻す

CPU、UART、SPI、SDカード、映像出力を一度に動かすと、原因候補が多すぎます。問題が出たら、観測できる最小構成へ戻します。

たとえばload/storeなら次の順に確認します。

1. メモリ単体で書いて読める
2. 固定アドレスだけで読める
3. CPUの1回の `sw` と `lw` を動かす
4. 複数アドレスへ広げる
5. UARTから結果を表示する

直前に機能を追加した場所だけでなく、その機能によって変わったタイミングや配線も調べます。

## FPGAのメモリには形がある

HDL上では同じ配列に見えても、書き方によってFPGAのBlock RAMになったり、論理素子の集まりになったりします。Block RAMは容量を効率よく使えますが、同期読み出しになることが多く、アドレスを出した次のクロックにデータが現れます。

確認する項目は次です。

- 合成レポートで想定したBlock RAMが使われたか
- 読み出しが何クロック後に返るか
- read enableやwrite enableの極性が合うか
- byte write enableが正しい位置に対応するか
- 初期化ファイルが合成ツールへ渡っているか

シミュレーション側も実機と同じ待ち時間を持つモデルに近づけると、差を早く発見できます。

## クロック制約とタイミング

組み合わせ回路の計算が次のクロックまでに終わらないと、実機では誤った値を取り込む可能性があります。配置配線後のタイミングレポートで、要求したクロック周波数を満たすか確認します。

失敗した場合は、いきなり条件を緩める前に長い経路を確認します。大きなデコーダ、広いMux、メモリからALUを通って書き戻す経路などが候補になります。後のパイプライン化は、長い処理を段階へ分ける方法の一つです。

## 外部入力は内部クロックと別の世界

ボタン、UART Rx、SPI MISOは、FPGA内部クロックと都合よく同時には変化しません。非同期入力をそのまま複数の回路で使うと、値の見え方がそろわない場合があります。

単bitの状態信号は同期用フリップフロップを通します。複数bitのデータは、ready/valid、FIFO、決められた通信プロトコルなどでまとまりを保ちます。

## 観測点を作る

実機の内部信号は、そのままでは見えません。開発ではUART出力やロジックアナライザを使って段階的に確認しました。

- GPIOやLED：到達した状態を少数bitで示す
- UART：PC、命令、エラー番号などを文字で出す
- 外部ロジックアナライザ：SPIやUARTのピン波形を見る
- FPGA内蔵ロジックアナライザ：内部バスや状態機械を見る

観測用信号を増やしすぎると回路規模やタイミングが変わるため、原因候補を絞って選びます。

## 「どこまで正しいか」を印にする

起動処理の各段階で短い印をUARTへ出す方法が有効です。

```text
A: reset後にCPUが動いた
B: メモリを読めた
C: SPI初期化を終えた
D: SDカードが応答した
```

最後に見えた文字から、次に調べる範囲を絞れます。数値を大量に出す前に、1文字ずつのチェックポイントから始めます。

## よくある切り分け表

| 症状 | 最初に見る場所 |
| --- | --- |
| 何も出ない | reset、クロック、ピン制約、UART設定 |
| 毎回同じ場所で止まる | 状態機械、ready/valid、メモリ待ち時間 |
| 実行ごとに結果が違う | 非同期入力、未初期化レジスタ、タイミング |
| byte順が逆 | エンディアン、シフト方向、配線 |
| 速度を下げると動く | タイミング制約、外部デバイスの最大周波数 |

原因を決めつけず、観測結果から候補を一つずつ減らします。開発履歴だけではChiselそのものを不具合原因と断定できないため、記事でも言語ではなく実装と実機条件を調べます。

## 今回の到達点

シミュレーション、合成後の回路、外部配線を別の段階として確認できるようになりました。以後のSDカードや映像出力でも、「要求を出したか」「相手が受け取ったか」「返事をCPUが使ったか」を観測します。
