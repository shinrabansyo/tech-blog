# 5段パイプラインとインターコネクトで、SoCを組み直そう

> タグ: CPU自作 / パイプライン / forwarding / hazard / interconnect / Veryl

1命令のfetchからwritebackまでを一度に進める構成は分かりやすい一方、1クロック内の経路が長くなります。処理を段階へ分け、別々の命令を重ねて進めるのがパイプラインです。

森羅万象CPUでは2026年2月に5段のpipeline coreを追加し、単一命令ずつ進めるcoreと実行traceを比較しました。同時期にCPU、メモリ、周辺回路をSoC moduleとしてまとめ、アドレスで接続先を選ぶinterconnectも追加しました。

## 5つのstage

実装は次のmoduleへ分かれています。

| stage | module | 主な仕事 |
| --- | --- | --- |
| F | `Fetch` | PCから命令を読む |
| D | `Decode` | 命令を解読し、レジスタを読む |
| E | `Execute` | ALU計算と分岐判定を行う |
| M | `MemAccess` | data memoryやI/Oへaccessする |
| W | `Writeback` | 結果をregister fileへ書く |

stage間にはregisterを置き、各クロックで次のstageへ情報を渡します。

```text
cycle 1: inst A [F]
cycle 2: inst A [D]  inst B [F]
cycle 3: inst A [E]  inst B [D]  inst C [F]
cycle 4: inst A [M]  inst B [E]  inst C [D] ...
cycle 5: inst A [W]  inst B [M]  inst C [E] ...
```

## data hazard

直前の命令が書く値を、次の命令が読む場合があります。

```text
add r4 = r5, r6
sub r7 = r4, r8
```

2命令目がDecodeにいる時点では、1命令目の値がまだWritebackされていない可能性があります。この依存関係をdata hazardと呼びます。

森羅万象CPUのcontrollerは、後段で得た新しい値を前段へ渡すforwardingを行います。複数の候補がある場合は、より新しい命令の結果を優先します。

load直後の値は、ALU結果より遅く届きます。次の命令がその値を使うload-use hazardでは、必要なstageをstallし、命令を1回待たせます。

## control hazard

分岐結果がExecuteで決まるまで、Fetchは次の命令を読み始めています。実際の分岐先と読んだPCが違えば、誤って進めた命令を無効にし、正しい場所からfetchし直します。

この無効化をflushと呼びます。森羅万象CPUのcontrollerは分岐先の不一致を検出し、Fetch/Decode側のstage registerをflushします。

```text
予想した次のPC ─┐
                  ├─ 一致 → 続行
実際の分岐先 ────┘  不一致 → 誤った命令をflush
```

## memoryとI/Oによるstall

cache miss、load応答、`isb`、UART、SPIは一定クロックで終わるとは限りません。後段が待っている間に前段だけ進めると、命令順やstage registerが壊れます。

controllerは次を見てstageごとのstallとflushを作ります。

- D-cacheが要求を受理できるか
- load dataが返ったか
- I-cacheへのwriteが終わったか
- I/Oのread dataまたはwrite readyが来たか
- store dataのforwardingが必要か

全stageを同じ理由で止めるとは限りません。後段の命令を保持し、空けるべき場所へbubbleを入れます。

## SoC moduleへまとめる

CPU coreの外に命令メモリ、データメモリ、IOBusを置き、`SoC` moduleで接続します。parameter `PIPELINE` によって単純な `Core` と `PipelineCore` を選べる構成が作られました。

```text
                    ┌─ instruction ROM
Core/PipelineCore ──┼─ instruction RAM
          │         └─ data RAM
          └────────── IOBus ─ UART/SPI/GPIO/Video
```

CPU内部へメモリを固定しないため、異なるcoreで同じ周辺回路を使い、結果を比較できます。

## addressで接続先を選ぶ

命令側ではinterconnectがaddress範囲を見てROMとRAMへ要求を振り分けます。2026年2月時点のSoC実装には、たとえば次の範囲設定があります。

```text
0x0000_0000 から 0x0000_0fff: instruction ROM側
0x0000_1000 から一定範囲   : instruction RAM側
```

要求時に選んだ接続先を、応答が返るまで保持します。存在しないaddressならdecode errorを返します。

実装内のinterface名には `axi_*` が使われていますが、この記事では**AXI風のsubset**として扱います。信号名が似ているだけでArm AMBA AXI規格への完全準拠を意味しません。準拠を主張するには、仕様で必須のchannel、順序、burst、応答条件などを個別に検証する必要があります。

## traceで2つのcoreを比べる

pipelineは同時に複数命令を持つため、波形だけでは最終的な実行順を追いにくくなります。そこで、命令が完了した時点のPC、命令、register write、memory accessなどを実行traceへ出します。

2026年2月18日の履歴では、single-cycle版とpipeline版のcommit logが一致することを確認しました。比較では、クロック数ではなく「完了した命令の順番と副作用」を合わせます。

```text
single-cycle trace: inst A, inst B, inst C
pipeline trace:     inst A, inst B, inst C
```

分岐でflushされた命令やstall中の同じ命令を、完了した命令として二重に記録しないことも確認します。

## 今回の到達点

5段pipeline、forwarding、load-use stall、branch flush、可変時間のmemory/I/O待ちを一つのcontrollerで扱いました。SoCとinterconnectへ分離したことで、single-cycle版と同じ外部構成を使ってtrace比較できました。

次はソフトウェア側へ戻り、動的メモリ確保とライブラリを整えます。
